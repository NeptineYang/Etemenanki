# 指标口径

- 状态：V1 设计基线
- 日期：2026-11-17
- 依据：DESIGN.md §8.1、§8.4，Q23
- 上位文档：[DESIGN.md](../../DESIGN.md)

## 1. 四种结果状态

| 状态 | 判定条件 | 计入行为已验证率 |
| --- | --- | --- |
| 行为已验证 | 目标构建通过、约定自动测试通过、人工审核通过、无未声明缺口 | 是 |
| 迁移完成 | 代码已生成，用户完成人工审核并接受剩余风险 | 否 |
| 实验结果 | 使用未知框架或未保证特性生成 | 否，单独统计 |
| 未完成 | 构建、测试、审核或支持检查未通过 | 否 |

状态按模块判定，项目状态取所有模块中最差的一个。不允许用项目级平均值掩盖失败模块。

## 2. 模块的定义

模块是状态判定与统计的最小单位，按以下优先级识别：

1. Maven 多模块项目的每个 `<module>`。
2. 单模块 Maven 项目按包根划分（`src/main/java` 下的顶层包）。
3. Python 项目按 `pyproject.toml` 声明的包或 `src/<package>` 目录。
4. 前端按 `package.json` 所在目录（单仓库多包时逐个计数）。
5. 无法归类的资源与配置并入其所属模块；独立的部署脚本与文档不计入。

同一项目的模块划分在整次迁移中保持稳定，不因生成结果变化而重新切分。

边界规则：

- 目录内存在多个构建文件时拆为多个模块，不合并统计。
- 生成代码与手写代码共存时，以 source map 与生成标记判定，生成部分不计入有效代码行。
- 无法归属的资源并入最近的上层模块；仓库根级脚本单列为 `root` 模块。
- 模块被阻断时仍计入分母，状态记为“未完成”，不允许从统计中剔除。

## 3. 有效代码行

- 统计对象：源项目的源文件，排除空行与纯注释行。
- 排除内容：`vendored/`、`node_modules/`、生成的代码目录、压缩与二进制资源、测试快照与 fixture 数据。
- 排除规则写在支持矩阵的 `exclusions` 中，随报告一起发布。
- 同一套统计口径同时用于“行为已验证率”的加权与单批次 5 万行上限，避免两个数字互相矛盾。
- 统计工具固定为 `tokei`，版本写入 `metrics/tokei.toml` 与报告；排除规则与支持矩阵的 `exclusions` 保持一致，不另写一套。

## 4. 行为已验证率

外部试点同时公布两种口径，分开写、不混用、不合并成单一数字：

**项目级**：`行为已验证的项目数 / 参与试点的项目总数`。只有全部模块都达到“行为已验证”的项目才算通过。

**模块级（按有效代码行加权）**：`Σ 已验证模块的有效代码行 / Σ 全部模块的有效代码行`。

报告中必须同时给出两个数字及各自的分子分母。只公布其中一个视为指标披露不完整。

## 5. 其他必报指标

- 构建成功率，按源项目与目标项目分别统计。
- 自动测试覆盖与未验证范围。
- 人工修改行数、审核时长、修复任务数、模型修复轮数。
- token 与模型成本、执行时长、性能回归。
- 失败类型分布、未支持特性清单、静默错误数（目标为 0）。

静默跳过受支持语义、伪造测试通过、隐藏外部契约变化属于阻断发布的问题，不是指标问题。

## 6. 试点与审核计时

试点选取规则（8 个项目）：

- 两套参考栈 × 两个方向各 2 个，覆盖 A/B 与 Java→Python、Python→Java。
- 至少 3 个没有可用测试，用来暴露“无基线”场景。
- 至少 2 个包含前端，用于视觉与 E2E 验证。
- 至少一半来自公开仓库且未被本项目任何提示词、映射或基准调优使用，作为保留集。

审核计时口径：从任务首次进入 `awaiting_review` 到最终批准的自然时间；标记为“等待外部信息”的暂停区间扣除，其余等待时间计入。同一项目多次审核只统计到最终状态。

## 7. V1-A 冻结项

- `tokei` 的具体版本与配置语法。
- 试点项目的最终名单与保留集划分。
- 性能阈值的项目级判定规则（不设统一“绝不劣化”）。
