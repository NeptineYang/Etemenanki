# 版本与发版

- 状态：V1 设计基线
- 日期：2026-11-17
- 依据：Q5、Q13–Q16、Q50、Q61–Q63
- 上位文档：[DESIGN.md](../../DESIGN.md) §12

## 1. 版本号

- 格式 `X.Y.Z`，全仓统一一个版本号：Core、Tauri 应用、CLI、Java/Python Worker、runner、环境定义共用同一版本。
- 不对各组件单独编号，避免发布时出现“Core 1.4.2 + runner 1.2.9”这类需要额外兼容矩阵的组合。
- 协议 schema 另有一份 `major.minor` 版本，独立于应用版本，见 [protocol.md](../design/protocol.md) §4。

## 2. 升位规则

| 变更类型 | 升位 | 触发方式 |
| --- | --- | --- |
| `feat`、`fix`、`refactor`、`data`、`build` | 最后一段 +1 | PR 合并后自动 |
| `docs`、`test`、`chore` | 不升版本，不打标签 | — |
| 复杂架构变化 | 中间位 +1，最后一段归零 | PR 带中间位标签 |
| 全新模块 | 中间位 +1，最后一段归零 | PR 带中间位标签 |
| 公开接口不兼容变更 | 中间位 +1，最后一段归零 | PR 带中间位标签 |
| `X.0.0` | 主版本 +1 | 只能手动触发 |

“公开接口”指 CLI 参数与退出码、报告与映射及 IR 的文件格式、Worker/runner 协议。本地 HTTP API 已取消，不再属于契约面。

默认每个 PR 都升版；`docs`、`test`、`chore` 例外，因为它们不改变发布物内容。里程碑 V1-A～V1-F 不与版本号挂钩，只写进 Release 说明。

## 3. 实现机制

- 构建清单中的版本号写占位值，PR 不修改版本号，避免每个 PR 都改同一批文件产生冲突。
- 构建时把版本号注入 Cargo、Maven、uv、npm 清单，产物内的版本由 CI 决定。
- PR 合并后，工作流按 PR 标题类型给合并提交打 `vX.Y.Z` 标签。标签是版本的唯一事实来源。
- 用 `GITHUB_TOKEN` 打的标签不会触发其他工作流。发布工作流必须由打标签的工作流显式调用，或改用 GitHub App token；否则在要求状态检查的分支保护下会卡住。
- `v*` 标签受保护：禁止删除、禁止强制移动。

## 4. 起始版本与 1.0.0

- 第一个需要升版的 PR 合并后打 `v0.1.0`。
- 0.x 全部标记为 pre-release，外部试点直接使用 0.x 版本。
- 满足 DESIGN.md §8.4 的 V1 退出条件后，手动触发 `1.0.0`。
- 不发布 rc 版本：0.x 已经承担了预发布角色。

## 5. 发布物与说明

- 每个版本都发布完整发布物清单，见 [delivery.md](../design/delivery.md) §5。环境包按内容寻址，未变化时复用同一文件。
- Release 说明取该版本对应 PR 的标题与链接，不维护 `CHANGELOG.md`，避免每次发版都要改 `main`。
- 发布失败时：保留标签但把 Release 标为 pre-release，修复后发新的 patch 版本；不移动已有标签。

## 6. 回溯策略

- 1.0.0 之前只向前修复，不建 `release/*` 分支。
- 1.0.0 之后是否维护 `release/1.x` 由当时的用户规模决定。
- 已发布版本的严重缺陷，在 1.0 之前一律以新 patch 版本修复。

## 7. 发布前验证

- 自动测试按 [ci.md](ci.md) 拆分执行。
- 完整的 Windows + WSL2 手工联调在 X.Y.0 的 PR 合并前完成，记录附在该 PR；触及 runner 或桥接的 patch 同样处理。
- 合并即正式发布，因此不存在“发布后再联调”的窗口。
